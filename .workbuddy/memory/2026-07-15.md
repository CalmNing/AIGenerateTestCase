## 缓存命中率仍低的二次排查（根因分析）

用户反馈命中率仍低。二次排查（代码审查 + mock transport 探针捕获真实请求体）确认：
- `enable_prompt_cache: True` 确实送达请求体顶层，`extra_body` 经 `with_structured_output` 保留，`tools` schema 跨调用一致，系统提示词全为静态常量，config 默认 `None`→自动开启。
- **结论：不是开关 bug，是结构性低命中。** 根因 = DeepSeek 磁盘 KV 缓存只缓存「前缀」，缓存单元锚定在「用户输入结尾/模型输出结尾」边界，公共前缀需跨多次请求检测后才持久化。可变 `requirement`（尤其接口测试粘贴的大段 API 规格）是输入主体且位于末尾 → 稳当前缀仅 system+tools(~4000 token)，需求一长整体命中率自然低；且规格嵌入可变需求文本中无法被复用命中。
- 次要：agent 路径把 MCP 工具名+描述拼进 system 提示词，工具集不同则前缀不同；公共前缀需≥2次同前缀请求才形成、空闲即清除。
- 注：DeepSeek 磁盘缓存默认自动开启，`enable_prompt_cache` flag 实为冗余（保留无害）。
- 真正解法：把 requirement 拆成「静态上下文(规格/约定/few-shot，放稳定前缀位置) + 动态指令(放最后)」，详见 `docs/cache-hit-root-cause.md`。

## 实现：拆分静态/动态前缀以提升缓存命中率（TDD）

基于根因分析落地结构性修复。新增 helper `_build_generation_messages(selected_prompt, core_requirement, selected_skill_names, api_context, is_api_test) -> (system_text, human_text)`：
- `system_text` = `selected_prompt` +（可选）技能方法论段落 +（可选）接口上下文段落 → 同一接口项目/技能组合逐字节一致，作为 DeepSeek 前缀 KV 缓存稳定锚点。
- `human_text` = 用户真实需求（接口测试加「补充背景」标签）→ 可变，放末尾。

### 改动文件
- `backend/utils/model_utils.py`：`generate_testcases` 新增 `api_context: str=""` 参数；移除「把 skill 正文 prepend 进 requirement」的逻辑；三路径（直连 function_calling / agent / ollama）统一用 `system_text` 作 system、`human_text` 作 human；历史保存改存 `human_text`。
- `backend/app/routes/testcase.py`：停止把 `api_context` 并入 `effective_requirement`，改为单独 `api_context=` 传参（前端无需改动，`api_context` 由服务端 `build_api_context` 生成）。

### 验证
- 新建 `tests/test_cache_prefix.py` 6 个用例（api_context 进 system 不进 human、skill 进 system、相同参数前缀逐字节一致、功能性无补充标签、无 api_context 时 system==base、三段组合顺序正确）全过。
- 全量 `tests/` 133 passed（原 127 + 6），无回归。

### 预期收益
同一接口项目连续生成时，大段 `api_context`（数千~上万 token）进入稳定前缀被命中；同技能组合下技能正文也被命中。功能性纯自由文本需求因本身可变收益有限（输入结构决定的理论上限）。

## 三次排查：pipeline 路径才是命中率低的真凶（非 HTTP/会话问题）

用户假设"HTTP 无状态 / 不一个会话 → 命中低"是**错误**的：DeepSeek 前缀缓存是服务端、按账号、按 token0 前缀 hash，与连接/会话无关。

**真因**：4 阶段 pipeline（`app/pipeline/pipeline_runner.py`）把一次生成拆成几十次独立调用，而每个阶段的 system 提示词（`REQUIREMENT_SPLITTER_SYSTEM` / `TEST_POINT_GENERATOR_SYSTEM` / `TEST_CASE_DESIGNER_SYSTEM` / `TEST_CASE_BATCH_OPTIMIZE_SYSTEM`）全部 **<1024 token**，低于 DeepSeek 可靠缓存门槛（≈1024 token）→ 基本不缓存，每次全价。主路径 `generate_testcases` 前缀已 4000+ token 能命中，但 pipeline 调用更频繁却几乎吃不到缓存。

**测量盲点（关键）**：pipeline 的 `TestPointGenerator`（`test_point_generator.py:77`）和 `TcDesigner`（`test_case_designer.py:80`）调 `_structured_output_robust` 时**没传 callbacks**，所以 `[缓存命中]` 日志在 pipeline 路径从不打印——对这条多调用路径命中率是"盲"的。

**杠杆**：A) 给每个 pipeline 阶段加 ≥1024 token 的共享静态前缀（api_context/方法论 few-shot 前置且逐字节一致）；B) api_context 从 user 移到共享 system 前缀（主路径已做，pipeline 未做）；C) pipeline 也接 `_TokenUsageCallback`；D) 实测 usage 字段确认埋点读真值。详见 `docs/cache-pipeline-analysis.md`。

## 四次排查：基于 DeepSeek 官方规则的命中率低根因（纯分析，未改代码）

用户明确：不改 token/cache 计算，只需按 DeepSeek 公开信息排查原因 + 给方案。结论写入 `docs/cache-hit-deepseek-analysis.md`。

**DeepSeek 官方硬约束（news0802 + 定价页）**：缓存默认自动开启（enable_prompt_cache 冗余）；前缀须从 token 0 起逐字节一致、中间匹配不算命中；64-token 存储单位；V4 可靠命中实用门槛 ≈1024 token（第三方实测，非官方硬下限）；缓存构建需秒级 + best-effort + 空闲清除 TTL；按账号隔离（与连接/session 无关）；监控字段 `prompt_cache_hit_tokens`/`prompt_cache_miss_tokens`；命中价≈未命中 1/50。

**实测结构**：主路径 system 已含 base+skill+api_context（>1024，应命中）；pipeline 4 阶段 system 均 <1024，且 `api_context` 在阶段2 位于 user 头部（`test_point_generator.py:62`）、阶段3 位于 user **尾部**（`test_case_designer.py:59` 的 `API_TEST_CASE_DESIGN_USER`），所有阶段都不在 system → 最大可复用块未进可缓存前缀，阶段3 那块成不可复用尾部。

**根因**：A) api_context 不在从0起前缀且阶段3 放尾部 → 跨批次零共享（头号原因）；B) pipeline 各阶段 system <1024 + 4套不同 system → 跨阶段/跨点零共享；C) 主路径与 pipeline 把 api_context 放不同消息位置 → 缓存碎片化；D) TTL+并发(gather)首轮必 miss；E) pipeline 没接 `_TokenUsageCallback` → 命中率测量盲点。已排除"HTTP/会话"假设。

**方案（未实施，仅供用户决策）**：1) api_context 提进 system 前缀且所有阶段布局一致（含阶段3 移出尾部）；2) 给每阶段补 ≥1024 token 静态方法论块；3) 可变内容一律放末尾；4) 先暖缓存再并发；5) 主/pipeline 统一前缀模板；6) pipeline 补埋点（验证前提）；7) MCP 工具列表确定性排序（低优先级）。

## 实施：pipeline 路径缓存前缀重构（方案①②③⑤⑥）

按 `docs/cache-hit-deepseek-analysis.md` 落地，目标是提升 DeepSeek 前缀缓存命中率（未改 token/cache 计算逻辑）。

### 核心改动
- `backend/app/pipeline/prompts.py`：
  - 新增 `SHARED_CACHE_PREFIX`（1907 字符的通用测试方法论静态块，跨过 ≈1024 token 门槛）+ `build_stage_system(stage_specific, api_context="", is_api_test=False)` → 返回 `SHARED_CACHE_PREFIX [+ 接口上下文块] + 本阶段专项指令`。保证 4 阶段、所有需求点、所有批次的开头逐字节一致 → 跨阶段/跨点/跨批次共享前缀缓存。

## 核查：无接口（功能测试）路径提示词加载是否正确

用户要求检查"不存在接口"情况下提示词加载。实测 4 阶段功能路径（`is_api_test=False, api_context=""`）：
- 4 个 agent 均正确走 `else` 分支，使用功能专用 system 模板（REQUIREMENT_SPLITTER_SYSTEM / TEST_POINT_GENERATOR_SYSTEM / TEST_CASE_DESIGNER_SYSTEM / TEST_CASE_OPTIMIZER_SYSTEM），`api_context` 未被注入 system、user 中无"API 接口信息"锚。
- `build_stage_system` 在无接口时返回 `SHARED_CACHE_PREFIX + 本阶段专项指令`，不含"## 接口上下文"段 → 功能与接口前缀可共享（功能是接口前缀的严格前缀）。
- 模板 `.format()` 安全：需求文本含花括号 `{}` 也不会崩（因按值传入，非模板解析）。
- 结论：无接口路径加载正确，无 bug。唯一小瑕疵：`SHARED_CACHE_PREFIX` 含一小段"接口测试补充说明"，对纯功能测试略显多余但无害。
