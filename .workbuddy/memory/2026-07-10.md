### 结论（已用实证推翻早期错误判断）
- 该接口**确实走 model_utils**。
- 但原始代码在**有效输入**下完全正常。实测：还原 model_utils.py 到原始版 + 真实需求文本 → `status=completed, error=null`，需求点5/测试点33/用例33。
- 早期那次"失败"纯粹因为 curl 里 `requirement_text=1` 是**退化输入**，模型返回 `requirement_points: []`。
- 早期我提出的"根因 = deepseek-v4-flash 推理模型 tool_choice 400 → 走死 fallback"**不成立**：真实失败是空列表路径（非 None、非异常），且原始代码用真实输入可正常完成。据此写的 model_utils.py "修复"**是多余的**，已 `git checkout` 还原，保持原样。

### 关键纪律（本次教训）
1. 异步接口即时返回 200 只代表"后台任务已启动"，真正成败在 `/pipeline/{id}/status` 轮询到的后台任务里。
2. **不要瞎改**：先完整追调用链，再用 A/B 实证（还原改动 → 跑原始 → 跑修复）确认根因，而不是凭第一次 API 报错就下结论。
3. 失败文案要区分：`"未生成任何需求点"`(空列表) vs `"需求拆分失败：模型返回空结果"`(None) —— 二者根因不同，前者通常是输入退化，后者才是模型/解析出错。

## 真正的需求/缺陷（用户澄清后）：generate-v2 应严格按接口 Schema 生成

### 用户意图
传入 `api_endpoint_id` 为主，核心是生成**接口测试用例**；`requirement_text` 只是辅助。应据接口 id 查 description/method/path/parameters，严格按 schema 生成。

### 真正的根因（v2 vs v1 行为不一致）
- `generate_v2`(pipeline.py:212-240) 已正确构建 `api_context`（含接口描述/路径/方法/参数/request-response schema/请求骨架-硬约束）。
- 但调用 `PipelineRunner.run` 时只把**原始 `requirement_text`** 传给阶段1(`splitter.analyze`)、阶段2(`tp_generator.generate`)；`api_context` **只**传到阶段3(`design_batch`)。
- 结果：阶段1/2 **完全没用接口 schema**，只靠用户文本 → 退化文本(`1`)时阶段1 返回空 → `未生成任何需求点` 失败。
- **v1 `generate`(testcase.py:507-513) 是对的**：`effective_requirement = api_context + "补充背景(次要)" + requirement`，schema 作主体、文本作辅助，整段喂所有阶段。v2 漏了这步。

### 已实施的修复（与用户确认的方案：显式传参 + 提示级约束）
1. `prompts.py` 新增 `API_REQUIREMENT_SPLITTER_SYSTEM/USER`、`API_TEST_POINT_GENERATOR_SYSTEM/USER`（接口测试变体，强调基于 schema、严格遵循请求骨架-硬约束、用户文本仅辅助）。
2. `RequirementSplitter.analyze(text, *, is_api_test=False, api_context="")` 与 `TestPointGenerator.generate(content, *, is_api_test=False, api_context="")` 增加显式参数；API 模式把 `api_context` 用**字符串拼接**作主体（禁用 `.format()`，因 api_context 含 JSON 大括号），用户文本作辅助。
3. `PipelineRunner._run_pipeline` 阶段1/2 及 `_inplace_update_test_points` 内的 `tp_generator.generate` 均透传 `is_api_test=is_api_test, api_context=api_context`。
4. 阶段3 `design_batch` 本就接 `api_context`，未改；`model_utils.py` 未改（维持原样）。
5. 功能测试（无 `api_endpoint_id`）走 `else` 分支，行为零回归。
