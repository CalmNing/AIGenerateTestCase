# 生成用例 Token 缓存命中率低 — 根因分析

> 排查日期：2026-07-15
> 结论：**不是缓存开关的 bug，而是 DeepSeek 磁盘 KV 缓存的边界机制 + 当前请求结构导致的结构性低命中。**

## 已验证（排除项）

通过代码审查 + 运行时探针（mock transport 捕获真实请求体）确认以下假设**不成立**：

| 假设 | 验证结果 |
|------|----------|
| `enable_prompt_cache` 没送达 | ❌ 不成立 — 探针确认请求体顶层含 `enable_prompt_cache: true` |
| `extra_body` 经 `with_structured_output` 被丢弃 | ❌ 不成立 — `build_chat_model` 的 `extra_body` 完整保留并随调用发出 |
| `tools` schema 每次调用不一致 | ❌ 不成立 — 两次调用 `tools` 完全一致（有界前缀稳定） |
| 系统提示词含动态内容（时间戳/uuid） | ❌ 不成立 — `prompts.py` 三段提示词均为写死常量 |
| config 开关默认关闭 | ❌ 不成立 — `prompt_cache_enabled` 默认 `None` → DeepSeek 主机自动开启 |

> 补充事实：DeepSeek 的 Context Caching on Disk **默认对所有用户自动开启**，无需 `enable_prompt_cache` 也能缓存。上一轮加的 flag 实际是冗余的（保留无害，但也不是命中的关键）。

## DeepSeek 缓存的边界规则（关键背景）

DeepSeek 磁盘 KV 缓存以**缓存前缀单元**为基本单位，**只有完整匹配某个已持久化的前缀单元才算命中**：

1. **请求边界持久化**：每个请求在「用户输入结尾」「模型输出结尾」两个边界产生缓存单元。
2. **公共前缀检测持久化**：系统检测到多个请求有共同前缀时，才把该公共前缀单独持久化为缓存单元。
3. **尽力而为**：不保证 100% 命中；空闲缓存通常几小时到几天内被清除。
4. 缓存单元以 64 token 为最小粒度，< 64 token 不缓存。

对生成用例场景：请求 = `system(静态) + tools(静态) + human(需求, 每次不同)`。
- 第 1、2 次请求因需求不同，边界单元互不匹配。
- 系统检测到 `system+tools` 为公共前缀后，第 3 次起才对 `system+tools` 部分命中。
- 若流量稀疏 / 类型或工具集频繁切换，该公共前缀单元可能尚未形成即被淘汰 → 持续低命中。

## 根因（按影响排序）

### 1. [主因] 可变内容（requirement）是输入主体且位于末尾 → 可缓存前缀占比小
DeepSeek 只缓存**前缀**。稳当前缀只有 `system + tools`（约 4000 token）。
而 `requirement`（尤其接口测试里用户粘贴的大段 API 规格 / 需求描述）往往是输入的主体，且每次都不同，位于消息末尾。
→ 即使 `system+tools` 完美命中，整体命中率 = `4000 / (4000 + 需求长度)`，需求一长自然很低。
→ 更糟的是：同一接口的规格被**嵌入在可变的人肉需求文本里**，每次需求微调就破坏了整段缓存，规格无法被复用命中。

### 2. [行为] 公共前缀需 ≥2 次同前缀请求才持久化，且空闲即清除
生成请求若稀疏、或在功能/接口/不同技能之间切换，DeepSeek 来不及形成并保留 `system+tools` 公共前缀单元。

### 3. [agent 路径] MCP 工具列表注入 system 提示词 → 前缀碎片化
`create_testcase_agent` 把 `tool_names` + 描述拼进 `TOOL_SYSTEM_PROMPT`。工具集不同 → 系统提示词不同 → 彼此不共享缓存；agent 路径与直连路径系统提示词也不同，跨路径不共享。
（上一轮已对工具名排序，但工具描述仍随工具集变化。）

### 4. [测量口径] 命中率 = cache_hit / 总 prompt token
即便 `system+tools` 完美命中，只要需求长，百分比就低。看到的「低」可能主要是这个口径问题，而非完全没命中。

## 真正能提高命中率的手段（按收益）

- **A. [最高收益] 拆分 requirement 为「静态上下文 + 动态指令」**
  把可复用的静态大块（API 规格、项目约定、few-shot 示例）从人肉需求文本中剥离，放到**稳定的缓存前缀位置**（独立的 system 级上下文，或固定在「指令」之前的一条消息）；把每次真正变化的指令放最后。
  这样同一接口反复生成时，大段规格被缓存命中，命中率可大幅提升。
- **B. 保持 `temperature=0`**（已设）→ 模型输出确定性高，利于「模型输出结尾」边界复用。
- **C. 同会话内连续生成同类型 / 同接口用例**，让 DeepSeek 尽快形成并保留公共前缀单元。
- **D. [可选] agent 路径对工具描述也做确定性排序**，或仅在真正需要时注入工具列表，减少前缀碎片化。

## 下一步建议
优先做 **A**：在 `generate_testcases` 入口把 `requirement` 拆成 `static_context`（规格等，稳定）与 `instruction`（指令，可变，置末尾），并相应调整 messages 组装。这是唯一能从结构上显著提高命中率的改动。
