# 测试用例生成：适不适合 Agent？——综合结论与改造路线

> 调研对象：本仓库（AI 测试用例生成与管理平台，FastAPI + SQLModel + LangChain/LangGraph）
> 调研时间：2026-11-02
> 证据分册（本目录）：
> - [01 现状事实地图](sections/01-current-architecture.md)：链路、agent 覆盖率、pipeline、上下文与提示词体量
> - [02 适配性判据与能力缺口](sections/02-fit-and-gaps.md)：7 条判据打分 + 7 项缺失能力（RAG/上下文/记忆/反馈/规划/评估/HITL）
> - [03 外部对标](sections/03-external-benchmark.md)：Meta/Qodo/Copilot 等实践、RAG 量化收益、RGA 术语澄清
>
> 全部结论附 `文件:行号` 或可点击 URL；本次调研未改动任何 backend/frontend 代码，未跑 pytest/uvicorn。

## 0. 一句话结论

**测试用例生成"部分适合"做 Agent，但当前形态还不是 Agent 任务，而是"一次性批式生成任务"。**

真正的答案不是"上不上 agent"，而是：

> **Agent 只在「有工具 + 有客观可判定的反馈 + 失败可重试」三条同时成立时才用。**
> 本项目只有两处局部同时满足（**文档获取/需求提取**、**接口用例 生成→执行→修复**），整体 4 阶段生成恰恰不满足（失败被静默吞掉、成本随数据线性放大）。

而用户点名的三件"缺的东西"，按优先级应当是：**失败可见性 > 记忆（checkpointer/thread）> RAG > 上下文工程 > 规划/反思 > HITL 回流**。RAG 不是第一位的——当前连"agent 有没有被用起来、失败有没有被看见"都还没解决。

> 注：用户提到的 **RGA 基本可判定为 RAG 的笔误**。检索到的 RGA 是 IEEE 2025 论文里的 *Relevance Generative Answering*（agentic RAG 中的相关性检测组件），与测试生成无关（见 [03 §4](sections/03-external-benchmark.md)）。

## 1. "现在到底有没有在用 Agent"——先破一个误解

多数人以为系统"已经在用 agent"，实际上：

| 典型输入 | 走向 | agent 参与 |
|---|---|---|
| 纯文本需求（最常见） | `_structured_output_robust` 直连 | ❌ |
| 纯文本 + 勾选 Skills | 同上（技能进 system 前缀） | ❌ |
| 接口测试（选端点） | 同上（api_context 进 system 前缀） | ❌ |
| 飞书/蓝湖链接，预取成功 | 注释原文"跳过 agent" | ❌ |
| 飞书/蓝湖链接，预取失败 | 直接抛 400 | ❌ |
| 文档链接 + MCP 工具 + 预取落空 | `create_testcase_agent` + `ainvoke` | ✅（窄区间） |
| Ollama 本地模型 | `ChatOllama.ainvoke` | ❌ |

- `create_testcase_agent` 全库**只有 1 个调用点**（`utils/model_utils.py:1202`），前提是"文档 URL + mcp:manage 权限 + 服务器可连通 + 预取落空且未抛错"四重条件。
- 4 阶段 pipeline **不是 LangGraph**（全库无 `StateGraph`），是写死的串行 `await`；`InMemorySaver` 在 `model_utils.py:146` 实例化后**从未传进 `create_agent`**，是死代码；`thread_id` 每次 `uuid4` 随机（`:1220`）。
- 因此：**当前系统的 agent 化程度 ≈ 0**，"要不要上 agent"是从零开始的设计题，不是优化题。

## 2. 适配性打分（7 条判据）

| # | 判据 | 结论 | 关键证据 |
|---|---|---|---|
| 1 | 需要外部工具/环境交互 | 部分契合 | 蓝湖/飞书/Swagger/Mock/真接口/浏览器能力**都在**，但全被放在 LLM 循环之外（预取或人工触发） |
| 2 | 多步、路径依赖、按中间结果改策略 | 部分契合 | 4 阶段是静态计划；阶段内并发互不可见；无"看结果改策略"的回边 |
| 3 | 有可验证反馈信号 | 部分契合 | 接口用例可真跑并回写 PASS/FAIL（`scenario_runner.py:292`），但**生成循环从不回读** |
| 4 | 状态需跨轮次/跨会话持久 | 部分契合 | 业务产物落库；**推理状态完全不持久**（checkpointer 未接、thread 每次新） |
| 5 | 输出需强结构化约束 | **契合** | 全链路 Pydantic schema + 三路 fallback + 归一化 + JSON 修复，是最扎实的一环 |
| 6 | 成本/延迟/确定性 | 部分契合 | temperature=0、有并发闸；但调用次数随数据线性增长、缓存结构性偏低、无 token 预算 |
| 7 | 失败模式可接受度 | **不契合** | 批次失败静默跳过、去重"保守保留"、任务仍标 completed；幻觉/漏分支无人可感知 |

**总评：契合 1 / 部分契合 5 / 不契合 1 → 部分适合。**

最致命的是第 7 条：agent 靠 error signal 自我纠错，而这个系统**把部分失败伪装成成功**。任何 agent 化都必须先修这条，否则 agent 会在没有反馈的环境里空转。

## 3. 三个"用户点名"的问题，逐个回答

### 3.1 RAG：完全没有，且当前做法在成本和缓存上双输

现状（唯一的"检索"）：
- `utils/helpers.py:736-764` `_build_history_context`：只查 `HistoryPrompt.content`，**最近 20 条**（`:695`）+ **精确 module_id 过滤**（无 session/user 过滤）+ **无字符截断**；
- 拼在**需求文本前面**、落在 **human 消息**（`model_utils.py:1126-1140`）→ 永远不命中前缀缓存；
- pipeline **完全不读历史上下文**（只有保存侧）；
- `requirements.txt` 无任何 embedding/向量/BM25 依赖；
- 技能里声明的 `get_existing_coverage`（`skills/coverage-analysis/SKILL.md:8`）**后端 0 实现**——等于给模型注入了一段它无法执行的指令。

外部量化（见 [03 §3](sections/03-external-benchmark.md)）：
- 相似用例做 few-shot：编译成功 +25.97%、通过率 +28.22%、覆盖率 +45.99%（CLAST, ASE'25）；
- 接口文档类 RAG：不改善正确率，只提行覆盖 +8.94%~+9.68%（arXiv 2409.12682）；
- **B 类（需求→步骤+预期用例）没有可信的公开量化**——别拿 A 类的数字当验收标准。

建议的最小落地（不引依赖）：**SQLite FTS5 检索 + 领域同义词词典 + top-k 放 system 前缀尾段**；向量检索留到有 eval 集、被证明不足之后再上。

### 3.2 上下文：有正确的骨架，缺预算与度量

- 已有的好设计：`_build_generation_messages`（`model_utils.py:978-1014`）把"提示词 + 技能 + api_context"放 system（可缓存前缀），需求放 human——这是对的。
- 缺的：**token 预算器、分级截断、长文档摘要、schema 瘦身**。
  - `api_context` 逐接口全量拼两段 JSON Schema 且**无截断**；
  - 历史 20 条无字符上限；
  - schema 固定税：`ResponseFormat` 5060 字符（≈1265 token）、单接口设计 schema 4404 字符——每次调用都付；
  - pipeline 6 个阶段配置里 **5 个 system 低于 ≈1024 token 的缓存实用门槛**（实测 573~987 token）→ 缓存形同未开；
  - pipeline 4 个 agent **未传 callbacks**，命中率是盲区。

### 3.3 记忆：这是硬伤，且是"接而未用"而非"没做"

- `InMemorySaver` 已导入、已实例化（`model_utils.py:14/146`），但 `create_agent`（`:633-638`）与 `chat.py:189-193` **都没有传 `checkpointer`**（全库 grep 仅 2 行命中）。
- `thread_id` 每次 `uuid4`（`:1220`）→ 即便挂上 checkpointer 也读不到历史，等价于每次冷启动。
- chat 无服务端记忆，消息靠前端每次全量回传；刷新即失忆。
- `HistoryPrompt` 是"清洗后的历史需求正文"，不是对话记忆，也不是长期事实记忆。
- **已验证**：`langchain.agents.create_agent`（langchain 1.3.0）签名确实含 `checkpointer` 与 `store` 参数 → 接入是"传参级"改动，成本极低。

Agent 里的**记忆**分三层，本项目三层都空：
1. 短期（会话轨迹）→ checkpointer 未接；
2. 长期（项目约定/已验证字段语义/人工确认案例）→ 无 Store、无载体；
3. 检索（历史经验）→ 见 3.1。

## 4. 该做 Agent 的三处 / 不该做的四处

### ✅ 该做（按 ROI 排序）

1. ~~**文档获取与需求提取**~~（**不适用，2026-11 用户确认**）
   原判断基于"预取失败常见"的假设（蓝湖 Cookie 过期 418、权限 401、页面超限）。
   实际情况：**只用飞书，基本无失败率** → agent 自愈的收益前提不成立，从"该做"移除。
   飞书路径现状已足够：预取成功直接走结构化输出（跳过 agent 是对的），
   失败时给出明确的 400 提示（引导检查 MCP 配置/access token）已是最合理的处理。
   蓝湖相关分支保留（不影响现有功能）但不再投入。

2. **接口用例"生成 → 执行 → 按失败修复"闭环**（收益最高）
   reward 客观可判：`scenario_runner.py:292` 真跑 + 断言引擎，失败信息结构化到步骤；零件齐全（`_run_validation` `testcase.py:74-135`、`regenerate_test_point` `pipeline_runner.py:1708`）。
   现状：`validation_status` **只有写侧、没有读侧**——生成链路从不读执行结果。这是把判据 3 从"部分契合"推到"契合"的唯一路径。循环上限 1~2 次即可。

3. **覆盖度驱动的补测**（需先补 RAG）
   技能层已写了方法论，但工具不存在。补齐"已覆盖清单"检索后，"查缺口→补用例→再校验"才是真 agent 循环；否则退化成又一次 LLM 猜覆盖。

### ❌ 不该做

1. **整体 4 阶段一次性生成**：成本/延迟随数据线性放大，缓存结构性偏低，且阶段内没有有效反馈信号。当前"固定 DAG + 并发批处理"是更优解，改成 agent 只会更贵更慢。
2. **用例文案优化/改名/补前置**：纯文本重写，输入输出确定，不需要探索。
3. **字段归一化、JSON 修复、endpoint_ref→endpoint_id 映射、数量对齐**：已有确定性实现，交给 LLM 只会降低确定性。
4. **去重**：当前用 LLM 语义判断且一律"保守保留"；更该做的是"确定性相似度 + 覆盖率证据"的指标化。

## 5. 落地路线（先地基、后 agent）

| 阶段 | 做什么 | 为什么在这个位置 | 成本 |
|---|---|---|---|
| **P0 修失败可见性** | 阶段失败进 task warnings、去重"保守保留"计数、级别分布校验、批次失败不再静默 | agent 的前置条件：没有 error signal 就没有 agent | 小（改 result/warnings 与校验） |
| **P1 接通记忆的骨架** | `create_agent(..., checkpointer=SqliteSaver)` + `store`；`thread_id` 从 `uuid4` 改为 `user+session+module` 稳定键 | 已在手、传参级改动；不做则任何 agent 都是"单轮工具调用" | 小 |
| **P2 检索（RAG 第一步）** | SQLite FTS5 + 领域词典 + top-k 放 system 前缀尾段；`TestCase` "已覆盖清单"摘要替代不存在的 `get_existing_coverage` | 成本零新增依赖；替代"最近 20 条"的时间排序 | 中 |
| **P3 执行反馈闭环** | 接口用例生成后自动 `_run_validation`，失败信息回灌下一轮（1~2 轮） | 唯一的客观 oracle，把判据 3 推到"契合" | 中 |
| ~~**P4 文档获取 agent 化**~~ | ~~预取失败不再直接抛 400~~ | **不适用（2026-11 用户确认）：实际只用飞书、基本无失败率。** agent 自愈无收益，已从路线图移除；蓝湖相关分支保留但不再投入 | 中 |
| **P5 上下文预算 + HITL 回流** | token 预算器、api_context 分级裁剪、长文档摘要；采纳/驳回 + 理由回流 | 前者控成本，后者给 agent 提供人类反馈标签 | 中~大 |

> 关键判断：**P0/P1/P2 做完再谈"全面 agent 化"**。跳过 P0 直接上 agent，等于让 agent 在没有反馈的环境里猜，成本上升而质量不动。

## 6. 判定标准（可直接拿去评审）

> **用 Agent 当且仅当三条同时成立：**
> ① 需要与环境/工具交互（不是纯文本变换）；
> ② 有客观可判定的反馈信号（能自动判定对错，不是"看起来合理"）；
> ③ 失败可重试且重试成本可接受。
>
> 三条对照：
> - 文档获取：①✅②✅③✅ 但**收益前提不成立**（2026-11 确认只用飞书、基本无失败率）→ **不做**
> - 接口用例执行修复：①✅②✅③✅ → **做**
> - 覆盖度补测：①✅②✅③✅（需先补检索）→ **做**
> - 4 阶段整体生成：①✅②❌（失败被吞）③❌（成本）→ **不做**
> - 文案优化/归一化/去重：①❌ → **不做**

## 7. 外部对标速查（为什么"过滤器"比"生成"更重要）

外部成熟方案（Meta TestGen-LLM / TestPilot / Qodo / Copilot / Diffblue）本质都是**生成测试代码**（A 类），共性套路是 **"多生成 + 客观过滤器（编译/运行/覆盖/变异）+ 人审"**，而不是"更聪明的 agent 循环"：
- TestGen-LLM：75% 可构建 / 57% 稳定通过 / 25% 提覆盖；人审接受 73%；
- Qodo 自述受控场景生成:可用 ≈ 1:4，真实仓库 ≈ 1:20，人审 ≈ 1:2 → **没有过滤器，生成器毫无价值**；
- Copilot Agent 也是"写→跑→失败→再改"，靠的是**能跑**。

本项目是 **B 类**（步骤+预期，无自动 oracle），应把 A 类的**过滤器思想**迁移过来：
- 用"测试点覆盖"当覆盖率，
- 用"执行断言结果"当编译通过，
- 用"确定性相似度"当 dedup，
- 用"人工驳回理由"当 HITL 反馈。

## 8. 三句话回答用户

1. **适不适合**：部分适合——但 2026-11 修正：原判断的"文档获取适合 agent"依赖"预取失败常见"的假设，用户确认只用飞书、基本无失败率 → **唯一值得做 agent 的是"接口用例执行修复"（已实现为 P3，默认关闭待开启）**。整体 4 阶段生成不适合做 Agent 的结论不变。
2. **缺什么**：最缺的不是 RAG，而是**失败可见性**（没有可靠 error signal）与**记忆接线**（checkpointer 已实例化却从未传入、thread_id 每轮随机）；其次是 RAG（当前是"最近 20 条"的时间排序，且落在不命中缓存的 human 消息里）。
3. **RGA**：基本可判定为 RAG 的笔误；检索到的 RGA 是 *Relevance Generative Answering*，与测试生成无关。
