# P5 上下文工程：token 预算与裁剪

> 对应 [docs/research/agent-fit-report.md](docs/research/agent-fit-report.md) 的 P5。
> 目标：给上下文装上"预算"，让它既不会静默超窗，也不会因为数据变多而成本失控。

---

## 〇、一个重要的认知修正（先说这个）

调研阶段说"pipeline 各阶段 system 提示词普遍 < ~1024 token，6 个配置里 5 个低于缓存门槛"
——**这个结论是错的**，错在估算口径。

仓库既有代码统一用 `chars/4` 估算 token（`utils/helpers.py:586-592`），
但**中文场景下 1 汉字 ≈ 1 token，`chars/4` 会低估 2~3 倍**。

用混合口径（CJK 1 字 ≈ 1 token，ASCII 4 字符 ≈ 1 token）重测：

| 内容 | chars/4 口径（旧） | 混合口径（准） | 是否达 1024 门槛 |
|---|---|---|---|
| `SHARED_CACHE_PREFIX` | 476 | **1487** | ✅ |
| 阶段1 功能/接口 | ~700 | 1803 / 1806 | ✅ |
| 阶段2 功能/接口 | ~800 | 2017 / 1828 | ✅ |
| 阶段3 功能/接口 | ~900 | 1978 / 2650 | ✅ |
| 阶段4 优化 | ~750 | 1800 | ✅ |
| 单次生成 功能 system | 878 | 2072 | ✅ |
| 单次生成 接口 system | 2279 | 4429 | ✅ |

**结论：前缀缓存其实一直是生效的**，不需要"补足前缀"。
P5 的真正价值在**预算与裁剪**，不在缓存。

> 这个修正也意味着：`docs/cache-hit-deepseek-analysis.md` 里基于 `chars/4`
> 得出的"阶段3 那块直接成了不可复用的尾部"等结论，需要用真实命中率重新验证。
> 本次已把 **3 个去重调用的埋点补齐**（此前唯一没有 callbacks 的地方），
> 下次真实运行即可看到 pipeline 的实际命中率。

## 二、实现

### 2.1 新增 `backend/utils/token_budget.py`

| 组件 | 说明 |
|---|---|
| `estimate_tokens()` | **混合口径**：CJK 1 字≈1 token，ASCII 4 字符≈1 token |
| `estimate_schema_tokens()` | schema 作为工具定义的 token 占用 |
| `truncate_text()` | 按字符截断，**优先在行边界断开**（不切碎 JSON） |
| `TokenBudget` | 按优先级分配预算；`reserve/allocate/remaining/over_budget` |
| `TruncationReport` | 裁剪报告（被裁了什么、省了多少） |
| `compact_api_context()` | api_context 分级裁剪（见 2.2） |
| `split_document_sections()` / `compact_document()` | 长文档按标题分段 + 逐段压缩（见 2.3） |

### 2.2 api_context 分级裁剪

- **核心接口**（用户显式选中的）：**保全文，永不裁剪**；
- **辅助接口**（依赖补全自动追加的）：压成骨架（方法/路径/必填字段），必要时只留接口名 + 明确标注"规格已省略"；
- 超得太多时：核心接口仍然保全文（哪怕超预算），并记录"核心接口本身已超预算"的告警。

> 为什么核心接口不裁：用户显式勾选的接口是他明确要求覆盖的范围，
> 裁掉等于直接丢失用户要的接口——这比超窗更糟。

### 2.3 长文档分层压缩

旧行为：`file_parser` 直接砍尾部（120000 字符），关键需求在末尾就**静默丢失**。

新行为：
1. 按 Markdown 标题 / 中文编号 / "第X章" 把文档切成段；
2. 含本次需求关键词的段落**保全文**（关键词从用户需求里抽取 2~4 字片段，不引分词库）；
3. 非重点段落压成前 200 字 + 明确标注"该段已压缩"；
4. 压不动才整体截断。

### 2.4 接入点

| 位置 | 接入内容 |
|---|---|
| 单次生成 `generate_testcases` | `_apply_token_budget()`：统一算预算 → 裁 api_context / 历史 → 裁文档 |
| pipeline `_run_pipeline` | 阶段 1 前裁 `api_context`（核心接口保全文） |
| 配置 | `model_window`（默认 32768）、`reserved_output_tokens`（默认 8192） |

### 2.5 裁剪可见性（P0 联动）

裁剪不是静默的：
- 裁剪产生 warning（`context_truncated` / `document_compacted`）→ 任务状态变 `partial`；
- warning 通过 `warnings_out` 回传路由层 → 前端进度面板展示"上下文已裁剪：…"；
- 裁剪报告含每项的前后 token 数与原因。

### 2.6 缓存埋点补齐

pipeline 的 3 个去重调用（需求点/测试点/用例）此前 `config={}` **没有 callbacks**，
是唯一看不见命中率的地方 → 已补 `_TokenUsageCallback`。

## 四、自检发现并修复的问题

| # | 严重度 | 问题 | 修复 |
|---|---|---|---|
| 1 | **严重** | **核心接口被裁**：`compact_api_context` 在预算不足时整体截断，把用户显式选中的接口也砍了 | 重写裁剪逻辑：核心接口保全文（哪怕超预算），只裁辅助接口；核心超预算时告警 |
| 2 | 中 | **口径错误**：沿用仓库既有 `chars/4` 估算，中文低估 2~3 倍 → 预算形同虚设、缓存门槛判断错误 | 新增混合口径 `estimate_tokens()`；并据此修正"pipeline 前缀不达标"的错误结论 |
| 3 | 中 | 文档硬截尾导致末尾关键需求**静默丢失** | 改为分层压缩（保留关键词段） |
| 4 | 低 | 去重调用无缓存埋点，pipeline 命中率是盲区 | 3 个去重调用补 `_TokenUsageCallback` |

## 五、测试

新增 31 个用例（`tests/test_token_budget.py`），全部不触网：

- 混合口径估算（中文/ASCII/混合/空/schema）；
- 截断（不截短文本、行边界优先、空输入）；
- 预算分配（预留、剩余、超预算、优先级 0 不可裁）；
- **api_context 分级**：核心保全文、辅助压骨架、核心永不丢、非核心接口名仍在；
- 文档分层（分段、保留关键词段、无标题兜底、压缩标注）；
- 报告累计（saved_tokens、items）。

回归：`backend pytest` **1102 passed**；前端 build/lint 通过（新增"上下文已裁剪"提示）。

## 六、这一版刻意**没做**的事

1. **没有改 schema 本体**：实测去掉 `description` 可省 37%（5060→3210 字符），
   但 `with_structured_output` 用 Pydantic 类，换成 dict 会失去校验，
   且 tool-calling 的参数识别可能受影响——**收益明确但风险更高**，
   在没有超窗实证前不动。当前只把 schema 体积**纳入预算计算**。
2. **没有做 token 预算的精确化**：估算仍是启发式（CJK 1 字=1 token），
   没有接 tokenizer 精确计数。
3. **没有做长文档的 LLM 摘要**：当前是"分段 + 保留关键词段"的规则压缩，
   没有额外花一次 LLM 调用做摘要（成本 vs 收益需实测）。
4. **没有把预算应用到 chat 路由**：chat 是自由问答，缺少"什么是核心"的语义边界。
5. **没有做提示词压缩**：`API_PROMPT`（7144 字符）里有大量示例，
   压缩它需要评估对生成质量的影响，属独立课题。
