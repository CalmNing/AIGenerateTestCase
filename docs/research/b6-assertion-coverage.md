# 断言覆盖率：根因分析与口径修正

> 基线暴露"断言覆盖率 13.9%"。本步查明：**这不是质量问题，是指标口径失真**；
> 真正值得改的是功能用例预期结果的"可判定性"，已通过提示词 + 新指标双管齐下。

---

## 一、根因：13.9% 是口径失真，不是生成质量差

旧口径把**所有用例**算进断言覆盖率分母。但两类用例的"断言"本质不同：

| 用例类型 | 量 | 断言覆盖 | 说明 |
|---|---|---|---|
| 接口用例 | 253 | **100%**（99% 带字段级 jsonpath 断言，均 4.96 条/用例）| 断言可执行、有 oracle（断言引擎真跑）|
| 功能用例 | 1359 | **2.8%** | FUNCTIONAL_PROMPT 明确声明"不需要 assertions"——**故意的** |
| 混算 | 1574 | 13.9% | 失真：把不该有 HTTP 断言的 86% 算进分母 |

功能用例没有 HTTP 断言是对的：它的 steps 是自然语言（"打开注册页面"），
没有响应结构可引用，硬造 `jsonpath_equals` 只会产生假断言。

## 二、真正的问题：功能用例的"预期结果可判定性"

功能用例的唯一验证依据是预期结果的**文字**。执行人靠它判断用例对错：

- ❌ 不可判定："操作成功" / "页面显示正常"（怎么算正常？）
- ✅ 可判定："订单状态从 PENDING 变为 APPROVED" / "提示语为「用户名不能为空」"

存量实测（新指标 `expected_verifiable_rate`）：**96.6%** 的功能用例预期已可判定，
约 45 条笼统。这比预想好——但提示词没有强制要求，新生成可能退化。

## 三、做的三件事

### 3.1 指标口径修正（`quality_metrics.py`）

`assertion_coverage_rate` 只统计**接口用例**（253 条，86.2%——真实水平）；
新增 `expected_verifiable_rate` 度量**功能用例**（1321 条，96.6%）的预期可判定性。
判定器（模块级 `expected_verifiable()`）：

- 可判定信号：具体对象关键词（状态/变为/跳转/提示语/字段/数量/URL…）、
  引用文案（「…」）、大写常量（APPROVED）、具体数值；
- 不可判定：只由笼统词（成功/正常/正确/显示/保存…）构成；
- 逐例验证过 8 个正反例；**启发式**，用于度量与提示，不是强规则。

### 3.2 FUNCTIONAL_PROMPT 强化（约束新生成）

- 把"功能测试不需要 assertions"改准确：加"预期结果本身就是验证依据"；
- 新增 **「预期结果必须可判定」** 章节：给出 ❌/✅ 对照例 + 硬规则
  （每条预期至少含一个具体可观察对象；状态变化写"从什么变成什么"）；
- 三个示例的笼统预期全部改为可判定写法（如"注册成功，跳转到登录页面"
  → "跳转到登录页面，URL 为 /login；用户列表出现 test_user_001，状态为「已启用」"）。

### 3.3 报告与快照更新

- 基线报告分行展示：`断言覆盖率（接口用例 253 条）86.2%` 与
  `预期可判定性（功能用例 1321 条）96.6%`；
- 快照存至 `docs/research/quality-baseline-after-assertion-metrics.json`。

## 四、A/B 验证方式（提示词改动如何证明有效）

提示词只影响**新生成**的用例，存量数据测不出提示词改动的效果。
验证闭环：

```bash
# 1) 记录当前功能用例的可判定率（96.6%）
python scripts/quality_baseline.py --save-snapshot before-prompt.json

# 2) 用新提示词生成一批功能用例（同一个需求，前后各跑一次）

# 3) 对新生成用例跑指标，对比 expected_verifiable_rate
python scripts/quality_baseline.py --session-id <新会话> --compare before-prompt.json
```

判定器行为已用 8 个正反例锁定（测试 `test_expected_verifiable_detection`）：
旧示例（含状态变化/文案）判可判定 ✅，纯笼统（"操作成功"×5）判 0% ✅。

## 五、测试

- `tests/test_quality_metrics.py`（27，新增 3）：口径修正回归
  （**断言覆盖率只算接口用例**——锁死旧口径 13.9% 失真的根源）、
  预期可判定性判定器 8 例、混合统计；
- 回归：`backend pytest` **1153 passed**；前端 build/lint 通过。

## 六、诚实的边界

1. 可判定性判定是**启发式**（关键词 + 词形），不是语义理解；
   "验证登录逻辑正确"这类不含笼统词但也不具体的预期会漏判——
   代价是少提示一句，可接受；
2. **提示词改动对新生成用例的实际效果尚未实测**——需要真实跑一次生成
   对比（要消耗 LLM 调用）；本步只保证了度量闭环与判定器正确；
3. 功能用例的"断言"终究要靠执行验证（UI 自动化，已有 browser_agent/hybrid_runner），
   那是另一个层面的闭环。
